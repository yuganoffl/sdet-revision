Lesson 05 · TestNG

Controlling execution

Which test runs first, what happens to the rest when one breaks, and the five @Test attributes that control a single method. Short lesson, heavy on interview questions.

The whole lesson in four lines

1. priority decides order. It protects nothing.
2. dependsOnMethods decides whether a test runs at all. A failed prerequisite means the dependent is skipped, not failed.
3. Skipped and failed are different verdicts, and knowing why is the interview question.
4. timeOut, expectedExceptions, enabled and invocationCount each control one method.

Two files in your repo run everything below: ExecutionOrderTest.java and TestAttributesTest.java.

Two problems that look like one

Lesson 2 showed that TestNG makes no promise about method order. Sooner or later that hurts, and people reach for priority to fix it. Half the time they have the wrong tool, because there are two separate problems here.

Ordering. Run the smoke check before the long one. Nothing breaks if you get it wrong, the report just reads oddly. That is priority.

Protection. Do not attempt the checkout test if login failed, because a checkout failure caused by a broken login is a lie in your report. That is dependsOnMethods.

Use the ordering tool for the protection job and you get a report full of failures that all trace back to one real bug.

priority

@Test(priority = -5) public void runsFirst()  { ... }
@Test               public void noPriority() { ... }   defaults to 0
@Test(priority = 3)  public void runsLast()   { ... }

Lower numbers first. Negatives are legal and useful, because they let you push a method ahead of the default without renumbering everything else. Two methods with the same priority run in an order TestNG does not define, so never rely on a tie.

The part nobody mentions

priority sorts methods within a class. It does not interleave across classes. I ran two classes inside one <test> tag, with priorities deliberately crossing over:

  priority -5        class A, all of it first
  no priority (0)
  priority 1
  priority 3
  [B] priority 0     class B, only now
  [B] priority 2

Class B's priority 0 did not jump ahead of class A's priority 3. Class order comes from the order you list them in testng.xml, which TestNG honours because preserve-order defaults to true. I reversed the two lines in the XML and the whole output flipped. So: XML decides class order, priority decides method order inside each class.

priority protects nothing

This is the trap. A lower-priority method that fails does not stop the ones after it:

  priorityFirstFails      FAILED
  priorityRunsAnyway  <-- still ran

Which is correct behaviour. priority is a sort key, nothing more. If you wanted the second one held back, you wanted a dependency.

dependsOnMethods

One real failure. Two skips. checkout depends on addToCart, which depends on login, so the whole chain came down from one broken link.

Why skipped and not failed

A skipped test never ran. It has proven nothing, good or bad. Reporting it as a failure would claim you found three bugs when you found one. This is the answer interviewers want, and it is why testng-failed.xml from lesson 3 contains skipped tests alongside failed ones: both still need proving.

alwaysRun

cleanupAnyway also depends on login, and it ran in both columns:

@Test(dependsOnMethods = "login", alwaysRun = true)
public void cleanupAnyway() { ... }

alwaysRun = true turns a hard dependency into a soft one: keep the ordering, drop the skipping. It is for teardown-ish work that has to happen whether the prerequisite worked or not. The same attribute on a @Before or @After method makes the configuration run even when its group is skipped.

A dependency beats a priority

Give a dependent method an earlier priority than the thing it depends on and TestNG ignores the priority:

@Test(priority = 5) prerequisite()
@Test(priority = 1, dependsOnMethods = "prerequisite") dependent()

  prerequisite (priority 5)     ran first anyway
  dependent (priority 1)

Dependencies are a constraint. Priority is a preference. Constraints win.

dependsOnGroups

dependsOnMethods names methods and breaks when you rename one. dependsOnGroups names groups instead, which survives refactoring and scales past a handful of methods:

@Test(groups = "auth")                     public void login() { ... }
@Test(groups = "auth")                     public void tokenRefresh() { ... }
@Test(dependsOnGroups = "auth")            public void checkout() { ... }

Now checkout waits for everything tagged auth, wherever it lives, even in another class. Groups are lesson 6.

The @Test attributes

TestAttributesTest.java has one of each, and the whole class passes. Run it:

mvn test -Dtest=TestAttributesTest
  finishesInTime
  runsThreeTimes
  runsThreeTimes
  runsThreeTimes
Tests run: 6, Failures: 0, Errors: 0, Skipped: 0

Six results from five methods, and one of the five never ran at all. Work out why before reading on.

What each attribute does
AttributeEffectUse it for
timeOut = 500fails the method if it runs past 500msanything that can hang: a wait, an API call, a locator that never resolves
expectedExceptions = X.classpasses only if X is throwntesting that bad input is rejected
expectedExceptionsMessageRegExpthe message must match toomaking sure it failed for the right reason
enabled = falsenot run, and not counted anywherequarantining a test. Always leave the ticket number next to it
invocationCount = 3runs the method three timessmoking out flakiness. Pair with threadPoolSize for concurrency
description = "..."text in the reportsaying what the test proves, in the report your manager reads

So: five methods, one disabled, one invoked three times. 4 + 3 − 1 = 6. enabled = false does not show up as a skip. It vanishes.

It passes if the exception is thrown anywhere in the method, including from your setup lines before you reach the call you meant to test. When the exact line matters, use a try/catch with an Assert.fail() after the call, or Assert.assertThrows(X.class, () -> ...), which scopes the expectation to one lambda.

Should tests depend on each other at all?

Mostly no, and saying so is worth more than reciting the syntax.

Dependencies make tests non-independent. You can no longer run one in isolation, the order is fixed so you lose parallelism across the chain, and one flaky prerequisite turns green tests yellow. The usual reason people reach for dependsOnMethods is that test two needs state that test one created, and the better fix for that is a @BeforeMethod that creates the state directly.

The legitimate uses are narrow and worth naming, because that is the answer that sounds experienced:

  • a login or token call that two hundred later tests need, where running them all against a dead session wastes twenty minutes and produces two hundred misleading failures
  • an environment health check that gates the suite
  • genuinely sequential workflows, where "add to cart" without "search" is not a test of anything

The one-sentence version for an interview: I use dependsOnMethods for real prerequisites like auth, so a broken login reports as one failure and two hundred skips instead of two hundred failures, and I avoid it everywhere else because it costs test independence.
