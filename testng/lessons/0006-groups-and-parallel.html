Groups, and running things at the same time

This lesson holds two separate topics. They share a lesson only because you configure both in testng.xml. Read part A, stop, then read part B. Do not try to hold both at once.

The two topics, one line each

A. Groups. Put a label on a test. The XML picks which labels run.
B. Parallel. One attribute decides which unit gets its own thread. Then shared state becomes a bug.

Part A: groups

The problem. You have four hundred tests. Before a merge you want ten of them. Overnight you want all four hundred. Before a release you want the payment ones. Writing three separate suite files means three class lists, and they drift apart.

The fix. Label the test method. Then filter on the label.

The label goes in the annotation. You already wrote this, in July, in SampleTest.java:

@Test(groups = "smoke")                      public void loginTest()
@Test(groups = "regression")                 public void checkoutTest()
@Test(groups = { "smoke", "regression" })    public void profileTest()
@Test                                        public void plainTest()    // no label

A test can carry many labels, or none.

The filter goes in the XML:

<test name="SmokeOnly">
  <groups><run>
    <include name="smoke"/>
  </run></groups>
  <classes><class name="com.sdet.studyplan.testng.SampleTest"/></classes>
</test>

groups-demo.xml, in your project root

That runs loginTest and profileTest. Two tests, not four.

The two rules that matter

Rule 1 — include means only these

A test with no groups attribute matches nothing, so it does not run. plainTest disappears. Nothing warns you. This is how somebody writes a new test, forgets the label, and it silently stops being part of the smoke suite.

Rule 2 — exclude beats include

Swap the include for <exclude name="regression"/> and profileTest vanishes, even though it is also tagged smoke. Being in one excluded group is enough to keep a test out, whatever else it is tagged with.

You can also filter from the command line, which is quicker while you are experimenting:

mvn test -Dtest=SampleTest -Dgroups=smoke

Two extras exist. <include name=".*smoke.*"/> takes a regular expression, so a naming convention becomes a filter. And <define name="all"> builds a group of groups, so all can mean smoke plus regression without retagging anything.

@BeforeGroups, the scope lesson 2 parked

Lesson 2 listed five scopes and deferred one. @BeforeGroups("smoke") runs once before the first method of that group, and @AfterGroups("smoke") once after the last, wherever those methods live.

   regression r1
@BeforeGroups smoke
   smoke s1
   smoke s2
@AfterGroups  smoke

It did not fire around r1. It fired once for two smoke methods. This scope hangs off a label rather than off the nesting boxes, which is why it never fitted the diagram.

Part B: parallel

Four hundred UI tests at fifteen seconds each is a ninety minute wait. Nobody runs a ninety minute suite before merging. One attribute on <suite> fixes that.

The rule, in three steps

How to read any parallel setting

1. The value names a unit. parallel="X" means one thread per X.
2. Count how many of that unit the suite has. That is your number of threads.
3. Everything inside the unit stays on one thread, in order.

Step 3 is the one people miss. The unit is the smallest thing that gets its own thread. Anything below it runs one after the other.

suite
 └── <test> tag      parallel="tests"     thread per tag
      └── class       parallel="classes"   thread per class
           └── method  parallel="methods"   thread per method

The same file, run four ways

parallel-demo.xml has two <test> tags, one class in each, three methods per class. Six methods in total. Every method prints its own thread name.

main    [A] a1

main    [B] b2
main    [B] b3

TagOne-2   [A] a2
TagOne-1   [A] a1
TagTwo-3   [B] b3
TagTwo-2   [B] b2
TagTwo-1   [B] b1

parallel="classes" — 2 threads

TagOne-1   [A] a1
TagOne-1   [A] a2
TagOne-1   [A] a3
TagTwo-1   [B] b1
TagTwo-1   [B] b2
TagTwo-1   [B] b3

parallel="tests" — 2 threads

tests-1   [A] a1
tests-2   [B] b1
tests-1   [A] a2
tests-2   [B] b2
tests-1   [A] a3
tests-2   [B] b3
Read the thread names, not the order

The order shuffles every run. It is noise. The thread name is the fact: it tells you how many workers there were, and which methods each one got.

valueunitthreads herewhat stays together
(none)nothing1everything, in order
tests<test> tag2all methods in a tag
classesclass2all methods in a class
methodsmethod6nothing

classes and tests both gave two threads. That is not a rule. This file happens to hold exactly one class per tag, so "split by class" and "split by tag" are the same split. Put three classes in one tag and classes jumps to four while tests stays at two.

tests versus methods, the difference that matters

Both make the suite faster. They differ in what they guarantee.

tests     tests-1:  a1 → a2 → a3        one thread, in order
          tests-2:  b1 → b2 → b3

methods   TagOne-1: a1 | TagOne-2: a2 | TagOne-3: a3     all at once
          TagTwo-1: b1 | TagTwo-2: b2 | TagTwo-3: b3

Under tests, a2 starts after a1 finishes. They share a thread, so they can share state safely.

Under methods, a1, a2 and a3 race each other. There is no order, and nothing they share is safe.

So methods is the fast one and the dangerous one. A suite can pass on tests for a year and fall apart the day somebody switches it to methods.

thread-count

<suite name="ParallelDemo" parallel="methods" thread-count="4">

thread-count is the ceiling, and it defaults to 5. Forty methods with thread-count="4" gives you four threads working through forty jobs, not forty threads. It is the size of the pool, not a promise: parallel="tests" with two tags uses two threads whatever you set.

Setting it to 1 makes the run sequential again. That is the quickest way to find out whether a failure is a real bug or a threading problem.

A fourth value, instances, threads by test-class instance and only matters when you use factories. Park it. Two switches also work without a suite file: @Test(invocationCount = 6, threadPoolSize = 3) runs one method six times, three at a time; and @DataProvider(parallel = true) runs lesson 4's rows concurrently. The provider pool is sized by data-provider-thread-count, a different setting from thread-count.

Part C: the part that actually bites

Everything above is one attribute. This is the reason parallel suites fail.

Two threads run the same class. They share one instance of it. So they share its fields.

private String shared;                                  // one box, two threads
private ThreadLocal<String> safe = new ThreadLocal<>(); // one box per thread

ThreadSafetyTest.java has two methods. Each writes its own value into both, sleeps, then prints what it reads back. Run it with thread-safety.xml, which is parallel="methods":

t2   shared=one   threadLocal=two
t1   shared=one   threadLocal=one

t2 wrote "two" and read back "one". The other thread overwrote the field while t2 was sleeping. The ThreadLocal column is right in both rows, because each thread got its own copy.

Run it three times and the corruption moves

Sometimes t1 is the corrupted row, sometimes t2. That non-determinism is the whole problem. The test passes on your laptop, fails in CI on a Tuesday, and passes again when you rerun it.

The framework answer, in one paragraph

This is why a parallel Selenium framework never keeps WebDriver in a plain field. It goes in a ThreadLocal<WebDriver>, usually inside a small DriverFactory. @BeforeMethod calls set(). The test fetches it with get(). @AfterMethod calls quit() and then remove(). Miss the remove() and the dead driver stays attached to a pooled thread, so you leak browsers. Say that in an interview and you have answered the most common framework design question there is.

Three other things break under parallelism, worth naming out loud: static fields anywhere in the framework, tests that share one login or one database row, and dependsOnMethods chains. TestNG honours dependencies under parallelism, so a long chain quietly serialises the speedup you just paid for.
