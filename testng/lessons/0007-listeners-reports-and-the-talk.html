Lesson 07 · TestNG

Listeners, reports, and describing it out loud

The last lesson. Two thirds of it is code you can run, and the last third is the part that actually gets you hired: saying what you built, in order, without waffling.

The whole lesson in four lines

1. A listener watches every test without any test knowing about it.
2. onTestFailure is where the screenshot goes.
3. IRetryAnalyzer reruns a flaky test inside the same run, and the retried attempts show up as skips in the report.
4. Reports are already being written. You have just never opened them.

Everything below runs from mvn test -Dsurefire.suiteXmlFiles=listeners.xml.

What a listener is for

You want a screenshot on every failure. You could put a try/catch in all four hundred tests. Nobody does that. Instead you write one class that TestNG calls at every interesting moment, and the tests stay ignorant of it.

ITestListener is the one you will use. Six methods, and the names say what they do:

ITestListener
MethodFiresReal use
onStartbefore a <test> tagstart a report, note the environment
onTestStartbefore each test methodlog the name, start a timer
onTestSuccessafter a passmark it green in a custom report
onTestFailureafter a failscreenshot, page source, browser console log
onTestSkippedafter a skiprecord why it never ran
onFinishafter the tagclose the report, print totals, email it

LoggingListener.java in your repo implements all six. There is no browser in this project, so instead of a screenshot its onTestFailure appends to target/test-failures.log. Same hook, same idea, an artifact you can open afterwards.

@Override public void onTestFailure(ITestResult result) {
    System.out.println("L>   FAIL    " + result.getName());
    // in a Selenium framework this line is the screenshot instead
    write(LocalTime.now() + "  " + result.getTestClass().getName() + "."
            + result.getName() + "  ->  " + result.getThrowable().getMessage());
}

Flip DEMO_FAILURE to true in ListenerDemoTest.java, rerun, and the file appears:

14:02:37  com.sdet.studyplan.testng.ListenerDemoTest.failsOnPurpose
          ->  deliberate failure for the listener demo expected [false] but found [true]

ITestResult is the thing worth knowing. It carries the method name, the class, the throwable, the parameters from your lesson 4 data provider, timings, and the ITestContext. Everything a report needs comes off that object.

The other interfaces exist and are worth being able to name: ISuiteListener wraps the whole suite rather than a tag, IInvokedMethodListener fires around configuration methods too, and IReporter runs once at the very end with the complete results, which is what report libraries hook into.

Retrying a flaky test

Lesson 3 promised this. testng-failed.xml reruns failures in a second run you start by hand. IRetryAnalyzer retries inside the original run, before TestNG decides the verdict.

public class RetryAnalyzer implements IRetryAnalyzer {

    private static final int MAX_RETRIES = 2;
    private int attempts = 0;

    @Override public boolean retry(ITestResult result) {
        if (attempts < MAX_RETRIES) {
            attempts++;
            return true;        run it again
        }
        return false;            give up, report the failure
    }
}
The counter must not be static

TestNG creates one analyzer instance per test method, which is what makes a plain field the right place for the count. Make it static and the first flaky test in the run burns the retries for every other test.

ListenerDemoTest.passesOnThirdTry fails twice then passes. Watch the listener and the analyzer interleave:

L>   start   passesOnThirdTry
R> retrying passesOnThirdTry (attempt 2 of 3)
L>   skip    passesOnThirdTry
L>   start   passesOnThirdTry
R> retrying passesOnThirdTry (attempt 3 of 3)
L>   skip    passesOnThirdTry
L>   start   passesOnThirdTry
L>   pass    passesOnThirdTry
L> done: passed=3 failed=0 skipped=2
Read that again, it is the interview question

A retried attempt fires onTestSkipped, not onTestFailure. So a screenshot-on-failure listener takes no screenshot for the attempts that were retried away. If you want evidence from every attempt, put the capture in onTestSkipped too, or in the retry analyzer itself.

It also means Surefire's per-suite line reads Tests run: 5, Skipped: 2 while the final summary reads Tests run: 3, Skipped: 0. Same run. The retried attempts are counted in one place and not the other, and that discrepancy confuses everybody the first time.

Retry every test without editing any test

Putting retryAnalyzer = RetryAnalyzer.class on four hundred methods is not a plan. IAnnotationTransformer rewrites the annotation as TestNG reads each method:

public class RetryTransformer implements IAnnotationTransformer {
    @Override public void transform(ITestAnnotation annotation, Class testClass,
                                    Constructor testConstructor, Method testMethod) {
        annotation.setRetryAnalyzer(RetryAnalyzer.class);
    }
}

Register it as a listener, and every @Test in the suite gets retries with no source change. Uncomment the second <listener> line in listeners.xml to see it.

A compile error you will hit

Those parameters are raw Class and Constructor, not Class<?>. TestNG 7.7 declares them raw, so the tidier generic version compiles to a different erasure and javac says does not override or implement a method from a supertype. I hit it writing this lesson. Keep them raw and add @SuppressWarnings("rawtypes").

Have an opinion about retries

Retrying hides flakiness rather than fixing it, and a suite that passes on the third attempt is a suite nobody trusts. The defensible position: retries are for genuinely external flakiness like a network blip, they are capped at one or two, and every retried test is logged so the flaky ones get fixed rather than tolerated. Say that and you sound like you have maintained a suite, not just built one.

The reports you already have

Every run has been writing these to target/surefire-reports/. Open them.

What lands where
FileWhat it is

emailable-report.htmlone self-contained page, built to paste into an email
<SuiteName>/<TagName>.xmlmachine-readable results per tag

When someone asks how you report results, the honest and complete answer has three layers. TestNG writes the HTML for a human. It writes JUnit XML for the CI server, which is what turns a build red and draws the trend graph. And a listener adds whatever the built-in reports cannot know, which in a Selenium framework means screenshots attached to the failures.

Two libraries get named a lot: ExtentReports and Allure. Both are listeners underneath. Knowing that they plug in through the same interface you just implemented is more useful than having used either.

Saying it out loud

This is the part that decides the interview. "Tell me about your framework" is not a knowledge question, it is a fluency question, and the failure mode is rambling through features in whatever order they occur to you.

Answer in four beats. Sixty to ninety seconds. Then stop and let them dig.

Beat 1 Shape

Maven project, TestNG as the runner, Page Object Model for the UI layer. Test data lives in Excel and is read with Apache POI. Suites are defined in testng.xml so CI can pick which slice to run.

Beat 2 Lifecycle and state

A base class holds the setup. The driver is created in @BeforeMethod and stored in a ThreadLocal so the suite can run in parallel, and @AfterMethod quits it and calls remove() so the pool does not leak. Anything shared across the whole run, config and connections, goes in @BeforeSuite.

Beat 3 Data and selection

Data-driven tests use @DataProvider, reading rows from Excel, so one test method covers as many cases as the sheet has rows and each row is a separate result in the report. Tests are tagged with groups, so the pre-merge run is smoke and the nightly is everything.

Beat 4 Failures and reporting

An ITestListener takes a screenshot in onTestFailure and attaches it to the report. Failed tests can be rerun on their own from testng-failed.xml. CI reads the JUnit XML, so a failure turns the build red.

Why this order works

It goes from the outside in: what it is, how it starts and stops, what it feeds in, what happens when it breaks. Each beat leaves an obvious question hanging, so the interviewer leads themselves into the follow-ups you already know: why ThreadLocal, why Excel and not JSON, what do you do about flaky tests.
