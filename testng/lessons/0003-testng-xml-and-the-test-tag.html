Lesson 03 · TestNG

testng.xml, and what <test> really means

One file decides which tests run and how. Lesson 2 left @BeforeTest as a word you had memorised. This lesson makes you watch it fire once, then twice, with the Java untouched.

The whole lesson in four lines

1. testng.xml is the file that says which classes run and how.
2. A <test> tag in it is a named bundle of classes, not a test case.
3. @BeforeTest fires once per bundle. Two bundles, two firings.
4. How many bundles there are is decided in the XML, never in the Java.

Everything below is you proving point 3 to yourself on your own machine. Read the first two sections, then start typing at Step 1.

Why the file exists

So far you have run tests with mvn test -Dtest=PalindromeTest. Fine for one class. It gives you no way to say the things a real suite has to say:

  • run these six classes, not those forty
  • run the smoke tests now, the slow ones tonight
  • run this bundle against staging, that bundle against production
  • run four classes at once, in separate threads

testng.xml is where you say them. It lives in version control next to the code, so how the suite runs gets reviewed like any other file. Your repo already has a tiny one, grouping.xml in the project root.

The four tags

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE suite SYSTEM "https://testng.org/testng-1.0.dtd">

<suite name="ScopeDemo">                    the whole run
  <test name="BothClassesTogether">           one named bundle
    <classes>                              just a wrapper
      <class name="com.sdet.studyplan.testng.AlphaTest"/>
      <class name="com.sdet.studyplan.testng.BetaTest"/>
    </classes>
  </test>
</suite>

You have already met three of these, from the other side. They are the same boxes as lesson 2's diagram, written down:

XML tag to annotation
TagWhat it isWrapped by
<suite>the whole run, one per file@BeforeSuite / @AfterSuite
<test>a named bundle of classes@BeforeTest / @AfterTest
<class>one Java class, fully qualified@BeforeClass / @AfterClass
(a method)one @Test@BeforeMethod / @AfterMethod

Class names carry the full package because TestNG loads them by name at runtime. A bare AlphaTest has nothing to resolve against, and the run dies with a class-not-found error.

The worst-named thing in TestNG

A <test> tag is not a test. It is closer to a chapter heading. One <test> tag routinely holds twenty classes and four hundred @Test methods. The word means one thing in Java and a different thing in the XML, and TestNG never fixes the collision. Read the tag as bundle every time you see it.

The experiment

You are going to run the same three Java files twice. Between the runs you change nothing but the XML, and the setup code goes from running once to running twice.

Step 1 Write the shared base class

Putting setup in a base class that test classes extend is how nearly every real framework does it, so this is worth typing rather than skimming. The name has no Test in it, which is what keeps Maven from trying to run it as a class of its own.

src/test/java/com/sdet/studyplan/testng/BaseLifecycle.java

package com.sdet.studyplan.testng;

import org.testng.annotations.*;

public class BaseLifecycle {

    private String who() { return getClass().getSimpleName(); }

    @BeforeSuite public void bs() { System.out.println("@BeforeSuite  for " + who()); }
    @BeforeTest  public void bt() { System.out.println("@BeforeTest   for " + who()); }
    @BeforeClass public void bc() { System.out.println("  @BeforeClass  " + who()); }
    @AfterTest   public void at() { System.out.println("@AfterTest    for " + who()); }
}

who() prints the subclass name, because getClass() on an inherited method returns the real object's class. That is how you will tell which class each line came from.

Step 2 Write two test classes that inherit it

They add nothing but tests. All four configuration methods come from the parent.

.../testng/AlphaTest.java

package com.sdet.studyplan.testng;

import org.testng.annotations.Test;

public class AlphaTest
        extends BaseLifecycle {

    @Test public void alphaOne() {
        System.out.println("      >>> AlphaTest.alphaOne");
    }

    @Test public void alphaTwo() {
        System.out.println("      >>> AlphaTest.alphaTwo");
    }
}

.../testng/BetaTest.java

package com.sdet.studyplan.testng;

import org.testng.annotations.Test;

public class BetaTest
        extends BaseLifecycle {

    @Test public void betaOne() {
        System.out.println("      >>> BetaTest.betaOne");
    }
}

Step 3 Run them in one bundle

Save the XML from the top of this lesson as one-test.xml in the project root. Two classes, one <test> tag. Then run:

mvn test -Dsurefire.suiteXmlFiles=one-test.xml

Step 4 Split them into two bundles

Same Java, untouched. Save this as two-tests.xml and run it. The only difference is that each class now sits in its own <test> tag.

two-tests.xml

<suite name="ScopeDemo">
  <test name="AlphaOnly">
    <classes><class name="com.sdet.studyplan.testng.AlphaTest"/></classes>
  </test>
  <test name="BetaOnly">
    <classes><class name="com.sdet.studyplan.testng.BetaTest"/></classes>
  </test>
</suite>
mvn test -Dsurefire.suiteXmlFiles=two-tests.xml

Count the highlighted lines. That is the entire finding.

How often each one fired
Method1 bundle2 bundlesBecause
@BeforeSuite1×1×one <suite> tag either way
@BeforeTest1×2×one firing per <test> tag
@BeforeClass2×2×two classes either way
There it is

Identical Java, different firing count. Nothing in the Java decided that. The XML did. @BeforeTest fires once per <test> tag, and the number of tags is a decision you make in a file.

Two smaller things in that output

@BeforeSuite ran once in both runs, even though two classes inherit it. Scope decides how often a configuration method runs. The number of classes that can see it changes nothing.

It said AlphaTest in one run and BetaTest in the other. TestNG picked an arbitrary instance to run the suite-level method on. So never write @BeforeSuite code that cares which class it hangs off.

What people use <test> tags for

Now that you can see the mechanism, the design makes sense. A <test> tag says these classes belong together and share a setup.

Real uses
WantShape
run the same classes on Chrome and on Firefoxtwo <test> tags, same classes, a different <parameter> in each
one browser shared by twenty related classesone <test> tag, browser opened in @BeforeTest
smoke suite and regression suite in one filetwo <test> tags with different group filters
run two bundles at the same time<suite parallel="tests">, one thread per <test> tag

That last row is why the scope exists at all. In lesson 6, parallel="tests" gives each <test> tag its own thread, which makes the tag the unit of isolation.

The suite file TestNG writes for you

One more thing falls out of "the suite is a file". If the suite is just a file, TestNG can write one. After any run with failures it does exactly that, and the file contains only the tests that failed. Rerunning them is then a matter of pointing at it.

mvn test -Dsurefire.suiteXmlFiles=target/surefire-reports/testng-failed.xml
Where the file actually is

Nearly every tutorial says test-output/testng-failed.xml. That is right when you launch from an IDE or plain TestNG. Through Maven, Surefire redirects TestNG's output, so on this project it lands in target/surefire-reports/testng-failed.xml, with a per-suite copy under target/surefire-reports/<SuiteName>/. Look in the wrong place and you conclude the feature does not exist.

Here is what a run of four methods, two of them failing, produced:

<suite name="Failed suite [FailedDemo]">
  <test thread-count="5" name="AllFour(failed)">
    <classes>
      <class name="com.sdet.studyplan.testng.FlakyDemoTest">
        <methods>
          <include name="failsTwo"/>
          <include name="failsOne"/>
        </methods>
      </class>
    </classes>
  </test>
</suite>

Same four tags you already know, plus one new pair. <methods> with <include> narrows a <class> down to named methods. You can write it by hand any time you want to run one specific test out of a large class. There is an <exclude> that does the opposite.

Skipped tests come along too

This is the part people get wrong in interviews. The file is not "the failures". It is "everything that was not proven to pass".

A chain of three, where login fails and the other two depend on it:

the run

@Test login()      FAIL
@Test addToCart() SKIP
@Test checkout()  SKIP
@Test unrelated() PASS

1 failure, 2 skipped

what it wrote

<methods>
  <include name="login"/>
  <include name="checkout"/>
  <include name="addToCart"/>
</methods>


unrelated() left out

All three skipped-or-failed methods are in. The one that passed is not. A test skipped because its prerequisite broke never ran, so it has proven nothing and belongs in the rerun.

Two rough edges

The file is overwritten on every failing run, so copy it elsewhere if you need to keep it. And rerunning it feeds its own name back through the generator, so a second round gives you Failed suite [Failed suite [FailedDemo]] and a tag named AllFour(failed)(failed). Harmless, but it looks broken the first time you see it in a report.

Not the same as retrying a flaky test

If someone asks "how do you handle flaky tests", testng-failed.xml is the wrong answer, because it needs you to start a second run by hand. The answer there is IRetryAnalyzer: you implement retry(ITestResult), return true for up to N attempts, and TestNG reruns the method inside the original run before deciding it failed. That is lesson 7, with listeners.

Two sentences, if you get asked in an interview. TestNG writes a testng-failed.xml after any failing run, holding the failed methods plus anything skipped because it depended on them, and you rerun by pointing your suite file parameter at it. For flakiness you use an IRetryAnalyzer instead, so the retry happens inside the original run.

Before the next lesson

Write your own testng.xml in the project root, with two <test> tags in it:

  • name the first Palindromes, give it PalindromeTest
  • name the second Samples, give it the SampleTest class already in your repo
  • run mvn test -Dsurefire.suiteXmlFiles=testng.xml
  • open target/surefire-reports/index.html and find both tag names

Then break something on purpose. Change one expected value in PalindromeTest so the assertion fails, rerun the suite, and finish with:

mvn test -Dsurefire.suiteXmlFiles=target/surefire-reports/testng-failed.xml

Read the Tests run: count on that second run. It should be 1, not the whole suite. Then put the assertion back.

TestNG writes that HTML report on every run. It is what interviewers mean when they ask "how do you report results".
