Lesson 04 · TestNG

@DataProvider, fed from an Excel sheet

One test method, twenty rows of input, twenty results in the report. This is the most asked-about feature in TestNG interviews, and the half you already wrote months ago is the Excel half.

The whole lesson in four lines

1. A @DataProvider is a method that returns rows of arguments.
2. A @Test bound to one runs once per row, and each row gets its own pass or fail in the report.
3. The rows can come from anywhere, because it is just Java. Excel is the common source.
4. Reading the sheet is Apache POI's job, not TestNG's. Keep the two apart.

Already in your repo

DataTable.readAsTable() in src/main/java/com/sdet/studyplan/excel/ turns a sheet into a List<Map<String,String>>, one map per row keyed by the header names. You wrote it in July. Its javadoc says "hand the list to a TestNG @DataProvider". This lesson is you cashing that in.

Why not just loop?

The obvious move is a for loop inside one @Test. It looks like it does the job. Here are both approaches run against the same three words, with hello deliberately marked as a palindrome so one row must fail.

Three things the loop got wrong, and all three are the answer when an interviewer asks why data providers exist.

The loop stopped at the first failure. A failed assertion throws, so racecar was never checked. You fix hello, rerun, and only then discover the next broken row. Twenty rows means twenty round trips.

The loop reported one result. "1 test, 1 failure" tells your manager nothing. The provider reported 3 tests and 1 failure, which is the true state of the system.

The loop hid which input broke. Look at the provider's failure name: isPalindrome[hello, true](2). TestNG puts the row's arguments in the test name for free. No logging, no message building.

The mechanism, with hardcoded rows

Learn it with no Excel in the way. This file is already in your repo.

src/test/java/com/sdet/studyplan/testng/DataProviderBasicsTest.java

public class DataProviderBasicsTest {

    @DataProvider(name = "words")
    public Object[][] words() {
        return new Object[][] {
            { "madam",   true  },
            { "racecar", true  },
            { "hello",   false },
            { "Madam",   false },
        };
    }

    @Test(dataProvider = "words")
    public void isPalindrome(String word, boolean expected) {
        Assert.assertEquals(Palindrome.usingTwoPointers(word), expected,
                "wrong verdict for '" + word + "'");
    }
}
mvn test -Dtest=DataProviderBasicsTest
Tests run: 4, Failures: 0, Errors: 0, Skipped: 0

One @Test method in the file. Four results. That is the whole idea.

Madam with a capital M is in there on purpose. Your usingTwoPointers compares characters directly, so case matters, and the sheet records that as expected behaviour rather than leaving it undiscovered.

The contract

What TestNG requires of a provider
RuleDetail
Return typeObject[][], or Iterator<Object[]> for large or lazily-read data
Outer arrayone element per test run. Four inner arrays means four runs
Inner arraythe arguments for one run, in parameter order
Method signaturethe @Test parameters must match the inner array in count and type
The name@DataProvider(name = "x") and @Test(dataProvider = "x") must agree. Omit name and it defaults to the method name
Where it livessame class by default. Elsewhere with @Test(dataProvider = "x", dataProviderClass = TestData.class), which is how real frameworks share one provider across many tests
Exceptionsit may declare throws. Useful, since reading a file does
The error you will hit first

Get the parameter count or type wrong and TestNG fails the test before your code runs, with a message about the data provider not matching the method signature. It is not a compile error, because the wiring happens by reflection at runtime. Read the message and count the columns.

This is the real argument for keeping data in a sheet. Adding a case is a row in Excel, and a tester who does not write Java can add it. Nothing recompiles.

Step 2 The reader you already wrote

DataTable.readAsTable("path.xlsx") gives you back:

[ {Word=madam,   Expected=true},
  {Word=racecar, Expected=true},
  {Word=hello,   Expected=false}, ... ]

Keyed by header name, so no magic column indexes anywhere in your tests. Rename a column in Excel and exactly one line of Java changes. The POI vocabulary underneath is one-to-one with what you see on screen: Workbook is the file, Sheet is a tab, Row is a line, Cell is a box.

Step 3 Wrap it in a provider

There are two shapes, and both are in ExcelDataProviderTest.java in your repo. Run them and compare.

Shape A: unpacked into typed arguments

@DataProvider(name = "wordsFromExcel")
public Object[][] wordsFromExcel()
        throws IOException {

    List<Map<String,String>> rows =
        DataTable.readAsTable(WORDS);

    Object[][] data =
        new Object[rows.size()][2];

    for (int i = 0; i < rows.size(); i++) {
        data[i][0] = rows.get(i).get("Word");
        data[i][1] = Boolean.parseBoolean(
            rows.get(i).get("Expected"));
    }
    return data;
}

@Test(dataProvider = "wordsFromExcel")

        String word, boolean expected) {

Shape B: the whole row as a Map

@DataProvider(name = "rowsFromExcel")
public Object[][] rowsFromExcel()
        throws IOException {

    List<Map<String,String>> rows =
        DataTable.readAsTable(WORDS);

    Object[][] data =
        new Object[rows.size()][1];

        data[i][0] = rows.get(i);

@Test(dataProvider = "rowsFromExcel")

        Map<String,String> row) {
    ...
}

Notice the only real difference. Shape A builds a [rows][2] array and the test takes two typed parameters. Shape B builds a [rows][1] array holding the map itself, and the test takes one.

mvn test -Dtest=ExcelDataProviderTest
Tests run: 14, Failures: 0, Errors: 0, Skipped: 0

Seven rows, two test methods, fourteen results. Neither test method mentions a single word of test data.

Which shape to use
A, typed argumentsB, a Map
Test reads as(String word, boolean expected), obvious(Map row), you dig inside
Typesconverted once, in the providereverything is a String until you convert it
Add a columntouch the provider and the signaturetouch nothing
Wrong column namefails in one place, loudlynull leaks into the test

Use A. Typed parameters are the reason the report says isPalindrome[hello, true](2) instead of a map's toString, and a provider is a good place to do conversion once. Reach for B when a sheet has fifteen columns and the test needs nine of them.

Four Excel gotchas

These are the ones that cost an afternoon. All four were reproduced on your machine while writing this lesson.

1. Numbers come back as doubles

That 12321 row exists to show this. POI stores numeric cells as double:

RAW  cell.toString()   -> 12321.0
FMT  formatCellValue   -> 12321

Imagine that cell is the password 123557 in your Apache.xlsx. Read it the raw way and you type 123557.0 into the login box, the test fails, and you go hunting through Selenium for a bug that is not there. DataFormatter.formatCellValue() returns what Excel displays, which is what you want in almost every case. Your DataTable already uses it.

2. A blank row in the middle silently truncates the data

This one was a live bug in your DataTable.java, and I fixed it while writing this lesson. The old loop bound was i < sheet.getPhysicalNumberOfRows().

sheet has 3 data rows with one blank line among them
before: readAsTable returned 2   racecar silently lost
after:  readAsTable returned 3

getPhysicalNumberOfRows() counts rows that exist. getLastRowNum() is the index of the final one. With a gap the count is smaller than the index, so the loop stops early and takes your last rows with it. The fix is one line:

// was
for (int i = 1; i < sheet.getPhysicalNumberOfRows(); i++)

// now
for (int i = 1; i <= sheet.getLastRowNum(); i++)

Note the <=. getLastRowNum() is an index, not a count. The existing if (row == null) continue; handles the gap itself.

Worth saying out loud in an interview

"A blank row in the middle of the sheet used to drop everything after it, because the loop used the physical row count instead of the last row index." That is a specific bug with a specific cause, and it is far more convincing than reciting that POI has a Workbook class.

3. Relative paths depend on where you launched from

"testdata/palindrome-data.xlsx" resolves against the process working directory. Maven runs from the project root, so it works. An IDE run configuration may not, and a module inside a multi-module build definitely will not. When it breaks, the file is fine and the path is wrong. Print System.getProperty("user.dir") before you doubt anything else.

4. .xls and .xlsx are different formats

XSSFWorkbook reads .xlsx. The older .xls needs HSSFWorkbook. Hand the wrong one an .xls and you get an exception about an invalid header signature. WorkbookFactory.create(file) picks the right one by sniffing the file, and is the better default in a framework you hand to other people.

@DataProvider vs @Parameters

Both feed values into tests, and interviewers like asking for the difference because the answer shows whether you have used either.

Two different jobs
@DataProvider@Parameters
Sourcea Java method, so a sheet, a database, an API, anything<parameter> in testng.xml
How many valuesmany rowsone value per run
Test runsonce per rowonce
Typesany objectstrings from XML, converted to primitives
Use it fortest data. Ten logins, forty search termsconfiguration. Which browser, which environment URL

The one-sentence version: @Parameters configures the run, @DataProvider feeds the run. A real suite uses both at once, with @Parameters("browser") from the XML deciding Chrome or Firefox while a provider pushes forty rows of data through whichever one started.

Three extras worth knowing they exist

@DataProvider(parallel = true) runs the rows in parallel threads. Fast, and a good way to discover your tests were sharing state.

Return Iterator<Object[]> instead of Object[][] when the data set is large. TestNG pulls rows one at a time rather than building the whole array up front.

A provider can declare a java.lang.reflect.Method parameter. TestNG passes the test method that is about to run, so one provider can return different rows depending on who is asking.
