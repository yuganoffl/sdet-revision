Lesson 02 · TestNG

The lifecycle annotations

TestNG's second job is running your tests. Ten annotations decide what happens around them, and one of them is named to mislead you.

The problem they solve

In lesson 1 your tests needed no setup. Real ones do. A Selenium test opens a browser. A database test opens a connection. An API test fetches a token. Put that work inside the test method and two things break: you repeat it in every test, and a failure in the setup gets reported as a test failure, which is a lie.

So TestNG lets you hang setup and teardown code around your tests. The only real question is how wide a net each piece of setup should cast, and that is what the ten annotations are for. They are not ten different features. They are one feature at five different scopes.

The five scopes

The scopes nest, strictly, like boxes inside boxes.

Read it from the outside in and you have the order the @Before methods run. Read it from the inside out and you have the order the @After methods run. There is no sixth rule to learn. Everything else follows from the nesting.

The fifth scope, @BeforeGroups and @AfterGroups, hangs off group membership rather than off the boxes. Park it until lesson 6.

Prove it yourself

Before you write anything, predict. Two test methods, all ten annotations, one class. Write down the order you expect on paper. Then create this file.

src/test/java/com/sdet/studyplan/testng/LifecycleDemoTest.java

package com.sdet.studyplan.testng;

import org.testng.annotations.*;

public class LifecycleDemoTest {

    @BeforeSuite  public void beforeSuite()  { System.out.println("@BeforeSuite"); }
    @BeforeTest   public void beforeTest()   { System.out.println("@BeforeTest"); }
    @BeforeClass  public void beforeClass()  { System.out.println("@BeforeClass"); }
    @BeforeMethod public void beforeMethod() { System.out.println("@BeforeMethod"); }

    @Test public void testOne() { System.out.println("    >>> testOne"); }
    @Test public void testTwo() { System.out.println("    >>> testTwo"); }

    @AfterMethod  public void afterMethod()  { System.out.println("@AfterMethod"); }
    @AfterClass   public void afterClass()   { System.out.println("@AfterClass"); }
    @AfterTest    public void afterTest()    { System.out.println("@AfterTest"); }
    @AfterSuite   public void afterSuite()   { System.out.println("@AfterSuite"); }
}

The import org.testng.annotations.*; is worth noticing. Ten separate imports is noise, and this is the one place a wildcard import earns its keep.

Read the shape, not the list

Nine of those lines printed once. The @BeforeMethod and @AfterMethod pair printed twice, once wrapped around each test. That is the only annotation pair that repeats, and it repeats because it is the innermost box. Learn the shape and you never memorise the list.

Now the part that matters

Look again at that output. @BeforeSuite, @BeforeTest and @BeforeClass all did the exact same thing: they printed once, in a row, at the start. With a single test class they are indistinguishable, which is precisely why people memorise the order and still get the concept wrong.

Add a second class and the difference appears. Here is the real output from running two such classes together, class [A] and class [B]:

[B] @BeforeSuite
[A] @BeforeTest      <- both classes' test setup, up front
[B] @BeforeTest
[B] @BeforeClass     <- class B's own setup, only now

[B] @AfterMethod
[B] @BeforeMethod
[B]     >>> testThree

[A] @BeforeMethod
[A]     >>> testOne
[A] @AfterMethod
[A] @BeforeMethod

Three things fall out of that, and all three are interview material.

Suite and test setup happen before any class starts. Both classes' @BeforeSuite methods ran before either class did any work. Suite scope means "before the whole run", not "before my class".

Class setup is bound to its own class. [A] @BeforeClass waited until class B was completely finished. It fires immediately before the first test method of that class.

Class order is not alphabetical, and method order is not declaration order. B ran before A. testFour ran before testThree. TestNG makes no promise about either. If your tests need an order, you must ask for one, which is priority and dependsOnMethods in lesson 5. If your tests need an order and you have not asked for one, you have a bug waiting for a slow day.

The trap in the name

@BeforeTest does not mean "before each @Test". That is @BeforeMethod. @BeforeTest means "before the classes inside one <test> tag in testng.xml" — the official wording is "run before any test method belonging to the classes inside the <test> tag is run". The word "test" is doing two unrelated jobs in this framework. Lesson 3 is entirely about the second job.

What real code goes where

Interviewers ask this as "where would you launch the browser?". The answer is always the same trade: wider scope is faster, narrower scope is safer.

Choosing a scope
AnnotationRunsPut this here
@BeforeSuiteonce per runread config, start a driver server, open a DB connection pool
@BeforeTestonce per <test> tagset up one browser or one environment that a whole group of classes shares
@BeforeClassonce per classlaunch the browser, log in once for a group of related checks
@BeforeMethodbefore every test methodreset state, clear cookies, navigate back to a known page
@AfterMethodafter every test methodscreenshot on failure, log out, clear test data
@AfterSuiteonce at the very endclose the connection pool, write the summary report

The honest default is @BeforeClass to open the browser and @BeforeMethod to return it to a known state. Opening a browser per method is correct but slow. Opening one per suite is fast but lets one test poison every test after it. Say that trade out loud in an interview and you sound like someone who has actually run a suite.
