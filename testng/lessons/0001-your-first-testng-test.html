Lesson 01 · TestNG

Your first TestNG test

You have run tests before. Today you write one, and hand the judging over to the machine.

The shift you are making

Every Java program in this repo ends the same way. A main method prints something, and you read the output and decide whether it looked right. Open Palindrome.java and you will find exactly that.

That works for three checks. It falls apart at three hundred, and it falls apart completely the moment someone else runs it, because the judgement lived in your head and nobody else has your head. A test framework moves the judgement into the code.

TestNG does three jobs for you, and it is worth naming them separately because interviewers ask about them separately:

  • It finds your test methods, so you never write main again.
  • It runs them, in an order and a lifecycle you control.
  • It judges them, and reports pass or fail without asking you.

Lesson 1 is only about the third job. The other two arrive in lessons 2 and 3.

Two words of vocabulary

Test method. An ordinary Java method marked with @Test. TestNG calls it. It must be public and it takes no arguments (until lesson 4, when data providers change that).

Assertion. A statement of what must be true. If it is true, nothing happens and the method keeps going. If it is false, it throws AssertionError and TestNG marks the test failed. That is the whole mechanism. A test passes by not throwing.

The consequence people miss

A test method with no assertion in it always passes. It cannot do anything else, because passing just means "did not throw". A test that prints and never asserts is theatre.

Write it

Create this file. Type it rather than pasting it, this once.

src/test/java/com/sdet/studyplan/testng/PalindromeTest.java

package com.sdet.studyplan.testng;

import com.sdet.studyplan.medium.Palindrome;
import org.testng.Assert;
import org.testng.annotations.Test;

// No main() method anywhere. That is the point.
public class PalindromeTest {

    @Test
    public void madamIsAPalindrome() {
        boolean result = Palindrome.usingTwoPointers("madam");
        Assert.assertTrue(result, "'madam' should be a palindrome");
    }

    @Test
    public void helloIsNotAPalindrome() {
        boolean result = Palindrome.usingTwoPointers("hello");
        Assert.assertFalse(result, "'hello' should not be a palindrome");
    }
}

Three details in that file are doing real work.

The location. It sits under src/test/java, not src/main/java. Maven treats those two trees differently: test code can see main code, main code cannot see test code, and test code is never packaged into the shipped jar. Put a test in the wrong tree and it either will not run or will ship to production.

The class name. PalindromeTest ends in Test, and that is not a style choice. Maven Surefire, the plugin that runs tests during mvn test, only looks at classes matching Test*.java, *Test.java, *Tests.java, or *TestCase.java (Surefire docs). Name it PalindromeChecks and mvn test will report zero tests and a green build, which is the most dangerous output in this entire lesson.

The second argument to the assertion. That message is what you will read at 2am when the build breaks. Write it as a statement of what should be true, not a description of the code.

Run it

mvn test -Dtest=PalindromeTest

-Dtest= narrows the run to one class. Drop it and Maven runs every test in the project. You should see this:

[INFO]  T E S T S
[INFO] -------------------------------------------------------
[INFO] Running com.sdet.studyplan.testng.PalindromeTest
[INFO] Tests run: 2, Failures: 0, Errors: 0, Skipped: 0, Time elapsed: 0.164 s
[INFO]
[INFO] BUILD SUCCESS
That is the win

Two methods you never called ran anyway, checked themselves, and reported. You wrote no main, no println, and no loop over test cases. TestNG found the methods by their annotation and did the rest.

Now break it on purpose

This half matters more than the green run. A test you have never seen fail is a test you do not yet trust. Change "hello" to "racecar" in the second method and run it again.

[ERROR] Tests run: 2, Failures: 1, Errors: 0, Skipped: 0 <<< FAILURE!
[ERROR] PalindromeTest.helloIsNotAPalindrome <<< FAILURE!
java.lang.AssertionError: 'hello' should not be a palindrome expected [false] but found [true]
    at org.testng.Assert.assertFalse(Assert.java:78)
    at ...PalindromeTest.helloIsNotAPalindrome(PalindromeTest.java:18)

Read that top line the way an interviewer would want you to. Your message comes first, then TestNG's own expected [false] but found [true], then the exact file and line. Notice too that the first test still ran and still passed. One failure does not stop the suite. Each test method stands alone.

Then put "hello" back and confirm it goes green again.

The assertion methods, and the one that catches people

Everything lives in org.testng.Assert, all static.

The assertions you will actually use
CallFails when
assertTrue(condition, msg)condition is false
assertFalse(condition, msg)condition is true
assertEquals(actual, expected, msg)the two are not equal
assertNotEquals(actual, expected, msg)the two are equal
assertNull(object, msg)object is not null
assertNotNull(object, msg)object is null
assertSame(actual, expected, msg)they are different objects in memory
fail(msg)always — for branches that should be unreachable
Interview trap

TestNG's order is assertEquals(actual, expected). JUnit's is the reverse, assertEquals(expected, actual). Get it backwards and your test still works, but every failure message lies to you about which value was which. Verified in the TestNG 7.7.0 source: public static void assertEquals(Object actual, Object expected).

Note that assertEquals on objects uses .equals(), while assertSame compares references with ==. That is the same distinction you met in Palindrome.usingReverse.
