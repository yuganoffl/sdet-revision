Lesson 01 · Selenium

Your first Selenium test

Open a browser. Find one thing on the page. Do something to it. Check the result. Close the browser. Every Selenium test you ever write is that loop, and by the end of this page you will have run it four times.

The whole lesson in four lines

1. WebDriver is the browser. By is how you describe what to look for. WebElement is what you got back.
2. driver.get(url), then driver.findElement(By.id("x")), then act on it. That is the loop.
3. findElement never returns null. It throws NoSuchElementException the moment it fails.
4. Finish with quit(), never close().

What is actually running

This is the part most tutorials skip, and it explains nearly every strange thing Selenium does later. Your test is not "in" the browser. Three separate programs are talking to each other.

  your TestNG test          chromedriver              Chrome
  (a Java process)   --->   (a local server)   --->   (the browser)
                     HTTP                     internal

  driver.findElement(By.id("name"))
        |
        +--> POST /session/<id>/element   {"using":"css selector","value":"#name"}
        <--  {"element-6066-...":"f3e2b1"}      a reference, not the element

Selenium speaks the W3C WebDriver protocol over HTTP. Three things follow from that picture, and each one saves you hours later:

  • Every single findElement is a round trip. A loop over a hundred rows makes a hundred network calls, which is why table loops feel slow.
  • A WebElement is a reference id the browser handed you, not a copy of the element. If the page redraws, that id points at nothing and you get StaleElementReferenceException. Lesson 4 deals with it.
  • chromedriver is a real operating-system process. Something has to kill it, and that something is quit().

The four types you will type every day

Learn these four and the rest of the API is variations
TypeWhat it isYou get one by
WebDriverThe browser session. An interface, so your test never mentions Chrome.new ChromeDriver(options)
ByA description of how to find something. It has found nothing yet.By.id("name"), By.cssSelector(..)
WebElementA handle to one element the browser did find.driver.findElement(by)
ChromeOptionsSettings handed to Chrome before it starts.new ChromeOptions()

By.id("name") on its own does nothing and touches no browser. It is a search instruction sitting in a variable. Confusing By with WebElement is the single most common beginner mix-up, and interviewers ask it on purpose.

Step 1 The page you will drive

Your first tests run against a file on your own disk, not a website. A beginner's first red test should be red for your reasons, not because a demo server took nine seconds to send a stylesheet. I have written it for you.

src/test/resources/pages/lesson1.html

<h1 id="title">Selenium practice page</h1>

<input id="name" type="text">
<button id="greet">Greet me</button>

<p id="message"></p>      <!-- filled in when the button is clicked -->

Open it in Chrome yourself first. Click the button. Whatever you are about to automate, do it by hand once, because you cannot write a test for a page you have not seen.

Step 2 Start and stop the browser

You know TestNG, so this costs you nothing new. @BeforeMethod opens a browser, @AfterMethod shuts it. One fresh browser per test method, which is what stops test three inheriting test two's typed-in name.

src/test/java/com/sdet/studyplan/selenium/FirstSeleniumTest.java

public class FirstSeleniumTest {

    private WebDriver driver;

    @BeforeMethod(alwaysRun = true)
    public void startBrowser() {
        ChromeOptions options = new ChromeOptions();
        options.addArguments("--headless=new");   // no visible window
        options.addArguments("--window-size=1450,900");
        options.setPageLoadStrategy(PageLoadStrategy.EAGER);

        driver = new ChromeDriver(options);   // Chrome starts here
    }

    @AfterMethod(alwaysRun = true)
    public void stopBrowser() {
        if (driver != null) driver.quit();
    }
}
Notice what is missing

No chromedriver download, no System.setProperty, no WebDriverManager. Selenium Manager ships inside Selenium and fetches the right driver itself (docs). It has done that since 4.6, and most tutorials you will find online predate it. If you say "I use WebDriverManager" on Sunday, the follow-up is "why?"

Step 3 Find something and read it

@Test
public void readsTheHeadingOffThePage() {
    driver.get(LOCAL_PAGE);                                // 1. go there

    WebElement heading = driver.findElement(By.id("title"));  // 2. find it

    Assert.assertEquals(heading.getText(), "Selenium practice page");  // 3. check
}

Three lines, and the third one is the only reason this is a test rather than a script. Without an assertion the code runs, prints nothing, passes always, and tells you nothing.

Step 4 Act on the page

There are really only two verbs at this stage. sendKeys puts text into a field. click clicks.

@Test
public void typesAndClicksAndChecksTheResult() {
    driver.get(LOCAL_PAGE);

    driver.findElement(By.id("name")).sendKeys("Yugan");
    driver.findElement(By.id("greet")).click();

    WebElement message = driver.findElement(By.id("message"));

    Assert.assertEquals(message.getText(), "Hello, Yugan!");
}

Note that findElement and the action are chained on one line. You only need a WebElement variable when you use the element more than once, as with message above.

Step 5 Meet your first exception

You asked to cover exceptions properly, so here is the first one, on day one. Ask for something that is not on the page:

@Test(expectedExceptions = NoSuchElementException.class)
public void findElementThrowsWhenNothingMatches() {
    driver.get(LOCAL_PAGE);

    driver.findElement(By.id("no-such-thing-on-this-page"));
}

This test passes because the exception is thrown. findElement does not return null, does not return an empty object and does not wait around. It looks once and throws.

Which leaves the question every beginner then asks, and it is the right question: what if the element is genuinely coming, just not yet? That is what waits are for, and it is lesson 3. For now, know that NoSuchElementException means one of two things. Your locator is wrong, or you looked too early.

The one pair of methods people confuse here
CallReturnsWhen nothing matches
findElement(by)one WebElement throws NoSuchElementException
findElements(by)List<WebElement> returns an empty list, throws nothing

That difference is a stock interview question. It is also the honest way to check whether something is absent: findElements(by).isEmpty(), never a try/catch around findElement.

Step 6 Run it

mvn test -Dsurefire.suiteXmlFiles=selenium.xml

Then run it again and watch Chrome actually do the work:

mvn test -Dsurefire.suiteXmlFiles=selenium.xml -Dheadless=false
RESULT ON THIS MACHINE

Tests run: 4, Failures: 0, Errors: 0, Skipped: 0 — two consecutive runs, 14 seconds each. Four browsers open and close, one per test method. Three tests hit the local file and are instant. The fourth hits a real website and is most of the 14 seconds.

The scary warning that means nothing

Every run prints WARNING: Unable to find CDP implementation matching 151, several times. Nothing is broken. Selenium 4.21 ships DevTools bindings for older Chrome builds than the 151 you have installed, and it says so loudly at startup. It only matters if you call the devTools API, which you never will in these lessons. Ignore it, but recognise it, because it looks like a failure and it is not.

What they will ask you on Sunday

Everything in this lesson is a question someone asks
QuestionThe answer, in one breath
What is WebDriver?An interface for driving a real browser over the W3C WebDriver protocol. ChromeDriver is one implementation, which is why I declare the field as WebDriver.
Difference between findElement and findElements? One returns a single element and throws NoSuchElementException if it is missing. The other returns a list that is simply empty.
close() or quit()?close() shuts the focused window. quit() ends the session and kills the chromedriver process. Teardown uses quit().
How do you manage the chromedriver binary?I do not. Selenium Manager has resolved it automatically since 4.6.
Why headless?Speed and CI. No window means no display server needed on a build agent. I turn it off locally when I need to see what happened.

Your turn

Twenty minutes. Do it before lesson 2, and type it rather than pasting it. The muscle memory is the point.

  1. Run the suite both ways, headless and not. Count the browser windows.
  2. Write a fifth test yourself. Type your own name into the field, click the button, and assert on the greeting. It is four lines and you have all four above. This is the first Selenium you will have written.
  3. Break it on purpose. Change By.id("greet") to By.id("Greet") and run again. Read the failure message from top to bottom, because that is the message you will spend the rest of your career reading. Notice that it tells you the locator it tried.
  4. Change quit() to close(), run the suite, then run pgrep -fl chromedriver in the terminal. Count what is still alive. Put it back.
