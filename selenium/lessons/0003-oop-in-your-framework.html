Lesson 03 · Selenium

OOP, and where each concept actually lives

Interviewers ask "explain the four pillars" and get a textbook definition back from everybody. The answer that stands out names the pillar, then points at a line of framework code. This lesson gives you both halves for each one.

How to answer any OOP question in an interview

Three sentences, in this order. What it means, in one line and in your own words. Where it is in my framework, naming a class. What it buys me, the problem it removes.

Definition alone sounds memorised. Definition plus a place sounds like you have used it.

1. Abstraction

What it means. Show what something does. Hide how it does it.

Where it lives, one: WebDriver itself. You have been using abstraction since lesson 1 without calling it that.

WebDriver driver = new ChromeDriver(options);

WebDriver is an interface. It declares get, findElement, quit. It contains no code that drives a browser. ChromeDriver supplies that. Your variable is the interface type, so the rest of the test cannot tell which browser it has.

Where it lives, two: the page object. This is the one to lead with.

// The test says what the user does.
loginPage.loginAs("yugan", "secret");

// The page object owns how it is done.
public HomePage loginAs(String user, String pass) {
    type(USERNAME, user);
    type(PASSWORD, pass);
    click(SUBMIT);
    return new HomePage(driver);
}

What it buys you. The login form gets redesigned. One method changes. The forty tests that log in do not.

2. Encapsulation

What it means. Keep the data private. Let people reach it only through methods you control.

People confuse this with abstraction constantly, so have the distinction ready. Abstraction hides complexity. Encapsulation protects state. Abstraction is a design idea; encapsulation is the private keyword doing a job.

Where it lives: the driver manager.

public final class DriverManager {

    private static final ThreadLocal<WebDriver> DRIVER = new ThreadLocal<>();

    public static WebDriver getDriver() { return DRIVER.get(); }

    public static void set(WebDriver driver) { DRIVER.set(driver); }

    public static void unload() {
        if (DRIVER.get() != null) {
            DRIVER.get().quit();
            DRIVER.remove();          // nobody can forget this now
        }
    }
}

The ThreadLocal is private. No test can touch it. That is what makes the remove() impossible to forget, which is the leak you saw in TestNG lesson 6.

Also here: locators in a page object are private static final By, never public. A test that could read LoginPage.USERNAME would start doing its own findElement, and the abstraction would rot within a month.

The one-rule version, worth saying out loud

"Nothing in my tests package imports Selenium. No By, no WebElement, no WebDriver. If a test needs one, my page object is missing a method." That single sentence demonstrates encapsulation, abstraction and design taste at once.

3. Inheritance

What it means. A class takes on the fields and methods of a parent, so shared code is written once.

Where it lives, one: BaseTest. Every test class extends it, so the browser lifecycle is written once instead of forty times.

public abstract class BaseTest {

    @BeforeMethod(alwaysRun = true)
    public void startBrowser() {
        DriverManager.set(DriverFactory.create(Config.browser()));
    }

    @AfterMethod(alwaysRun = true)
    public void stopBrowser() {
        DriverManager.unload();
    }
}

public class LoginTest extends BaseTest { ... }

Where it lives, two: BasePage, holding the driver, the wait, and the shared click and type helpers that every page needs.

What it buys you. One place to change how every test starts a browser. One place that owns every wait in the framework.

The follow-up they ask next: composition over inheritance

Inheritance is for "is a". A LoginTest is a test. A LoginPage is a page. Fine.

A header, a nav bar or a modal is not a page, and it appears on twenty pages. Do not inherit it. Compose it: the page holds one as a field.

public class HomePage extends BasePage {
    public final Header header = new Header(driver);   // composed, not inherited
}

Deep inheritance chains are the classic framework smell. Two levels is plenty.

4. Polymorphism

What it means. One name, many behaviours. It comes in two kinds and you should name both.

Runtime polymorphism (overriding)

The reference type is fixed at compile time. The object behind it is decided while running. This is how cross-browser works, and it is the best example you have.

public static WebDriver create(Browser browser) {
    switch (browser) {
        case CHROME:  return new ChromeDriver(chromeOptions());
        case FIREFOX: return new FirefoxDriver(firefoxOptions());
        case EDGE:    return new EdgeDriver(edgeOptions());
    }
}

Every branch returns a different class. The caller gets a WebDriver and cannot tell them apart. driver.findElement(...) runs Chrome's code or Firefox's code depending on what is actually there. Nothing in a test or a page object changes.

Say this and you have answered "how does your framework do cross-browser?" and "explain polymorphism" with one example.

Compile-time polymorphism (overloading)

Same method name, different parameters. The compiler picks.

protected void click(By locator) { click(locator, Config.defaultTimeout()); }

protected void click(By locator, Duration timeout) { ... }

The three follow-ups that come next

Interface or abstract class?

You have one of each in the framework, which makes this easy to answer concretely.

Interface is a contract with no state. Use it when unrelated classes need to promise the same behaviour. WebDriver is one: ChromeDriver and FirefoxDriver share no parent worth having, and a class can implement many interfaces.

Abstract class is a partly-built parent that holds shared state. BaseTest is one: it has a real @BeforeMethod body and it makes no sense to instantiate on its own. A class can extend only one.

One line to say: "Interface when I need a contract, abstract class when I have shared code and shared state to hand down."

static versus instance

Both are in DriverManager, and the reason is worth knowing. ThreadLocal is static so there is exactly one holder for the whole run, reachable from anywhere without passing a driver around. The value inside it is per thread. So the holder is shared and the driver is not, which is precisely the trick that makes parallel runs safe.

Why final on the locators?

private static final By USERNAME = By.id("user"); — static because the locator is the same for every instance, final because nothing should ever reassign it, private because of the rule above.
