Lesson 05 · Selenium

Exception handling

Two halves. The Java rules, which they will ask you cold. Then the Selenium catalogue: what each one means, why it happened, and the fix. Every exception below is thrown for real by a test in this repo, and the class hierarchy was read out of the jar rather than remembered.

The whole lesson in four lines

1. Checked means the compiler forces you to deal with it. Unchecked means it does not.
2. Every Selenium exception is unchecked. That is deliberate, and it is why tests let them fly.
3. In a test, catching an exception usually turns a real failure into a false pass. Let it propagate.
4. The five you must know by sight: NoSuchElement, Timeout, StaleElementReference, ElementNotInteractable, ElementClickIntercepted.

Part one: the Java rules

Checked versus unchecked

The whole distinction is one question: does the compiler force you to handle it?

Throwable
  ├── Error                  JVM-level. OutOfMemoryError. Do not catch these.
  └── Exception
        ├── RuntimeException     UNCHECKED. NullPointer, IllegalArgument, ...
        │                        Compiler says nothing.
        └── everything else      CHECKED. IOException, SQLException, ...
                                 Compiler forces try/catch or throws.

The line to say: "Checked exceptions are conditions a caller could reasonably recover from, so the compiler makes them part of the signature. Unchecked ones are programming errors, and forcing everyone to catch them would just produce empty catch blocks."

try, catch, finally

try {
    // work that might fail
} catch (IOException e) {
    // handle it, or rethrow with context
} finally {
    // runs whether or not it threw. Cleanup goes here.
}

finally runs even when the try block returns. That is what makes it the place for cleanup. In a test framework, though, cleanup belongs in @AfterMethod(alwaysRun = true), which is TestNG's version of the same idea.

throw versus throws

throw is a statement. It throws one object, right now. throws is part of a method signature. It declares what might come out. Interviewers ask this to check you are not guessing.

public Row read(int i) throws IOException {      // declares
    if (i < 0) throw new IllegalArgumentException("row " + i);   // throws
}

Custom exceptions, and when they earn their place

public class FrameworkException extends RuntimeException {
    public FrameworkException(String message, Throwable cause) {
        super(message, cause);        // keep the cause. Always.
    }
}

Worth it when you can add context the original could not carry. "Could not read row 7 of palindrome-data.xlsx" beats a bare IOException. Extend RuntimeException so it does not pollute every signature above it, and always pass the cause through, or you throw away the stack trace that tells you what really happened.

The part that matters for testing

A catch block in a test is usually a bug 
// Never do this.
try {
    driver.findElement(By.id("submit")).click();
} catch (Exception e) {
    System.out.println("could not click");
}

The button was missing. The application is broken. And your test just printed a line nobody reads and passed green.

A test's job is to fail when the application is wrong. Swallowing the exception is the one way to guarantee it cannot do its job.

So how do you assert that something should fail? Not with a catch block. Declare it:

@Test(expectedExceptions = NoSuchElementException.class)
public void noSuchElement() {
    driver.findElement(By.id("does-not-exist"));
}

That test passes because the exception was thrown, and fails if it is not. The intent is in the signature where a reader sees it.

Where catching is legitimate, and be ready to name these, because "never catch anything" is not a real answer:

  • In the framework, not the test. A BasePage helper that retries a click once on ElementClickInterceptedException.
  • To add context, then rethrow. Catch, wrap in your own exception with the row number and the URL, throw that. Never swallow.
  • In an @AfterMethod. Teardown that throws hides the real failure with a second one.
  • In a listener. A screenshot that fails must not take the report down with it.

Part two: the Selenium catalogue

Read out of selenium-api-4.21.0.jar with javap, not from memory:

RuntimeException
  └── WebDriverException              <- everything below is UNCHECKED
        ├── NotFoundException
        │     ├── NoSuchElementException
        │     ├── NoAlertPresentException
        │     ├── NoSuchWindowException
        │     └── NoSuchFrameException
        ├── TimeoutException
        ├── StaleElementReferenceException
        ├── InvalidSelectorException
        └── InvalidElementStateException
              └── ElementNotInteractableException
                    └── ElementClickInterceptedException
Three things that diagram tells you, and most people miss all three

1. WebDriverException extends RuntimeException, so every Selenium exception is unchecked. The compiler never forces a catch. That is a design decision: a broken locator is a programming error, not something the caller recovers from.

2. ElementClickIntercepted extends ElementNotInteractable. So catching the parent silently catches the child, and you swallow the cookie-banner bug you were hunting.

3. WebDriverWait ignores NotFoundException, which covers NoSuchElement. But StaleElementReference sits on a different branch, so it is not ignored. A wait over a rerendering element blows up unless you say .ignoring(StaleElementReferenceException.class). That is the real reason FluentWait exists.

The five you must know by sight

ExceptionWhat happenedThe fix
NoSuchElementException Nothing matched the locator, right now. Check the locator first, it is usually a typo. Then check you are on the right page or inside the right frame. Then add an explicit wait.
TimeoutException The locator may be fine. The condition never came true in time. Ask whether you waited for the right condition. Waiting for presence when you needed visibility is the usual cause.
StaleElementReferenceException You found it, then the page replaced that node. Your handle points at something the DOM threw away. Re-find it. A longer wait cannot help, because the wait already succeeded once. Do not store WebElement fields on a page object.
ElementNotInteractableException It is in the DOM but cannot receive input. Hidden, zero-sized, or off screen. elementToBeClickable, or scroll it into view. Check it is not display:none.
ElementClickInterceptedException Something is on top of it. A cookie banner, a modal, a spinner. Wait for the overlay to go with invisibilityOfElementLocated. Dismiss the banner. A JS click hides the problem rather than fixing it.

The rest, one line each

InvalidSelectorExceptionThe selector is malformed. Classic cause: XPath passed to By.cssSelector.
NoAlertPresentExceptionYou switched to an alert that is not open. Wait for alertIsPresent.
NoSuchWindowExceptionThe handle you switched to is closed. Re-read getWindowHandles().
NoSuchFrameExceptionWrong frame name or index. Remember to switchTo().defaultContent() on the way out.
SessionNotCreatedExceptionThe browser never started. Usually a browser and driver version mismatch.
WebDriverExceptionThe catch-all parent. Seeing this raw usually means the session died.
The one that throws nothing at all

Clicking a disabled button raises no exception. Chrome swallows it. Your test carries on and asserts against a page where the click never happened. Verified in lesson 2 by a test that failed when it expected ElementNotInteractableException.

An exception is the good case. It is the silent no-op that ruins your afternoon.

StaleElementReference, the one they probe

It is the favourite follow-up because it catches people who learned exceptions from a list. The trap: it sounds like a timing problem, so people add a longer wait, and it keeps happening.

WebElement row = driver.findElement(By.cssSelector("#list .row"));
row.getText();                              // fine

driver.findElement(By.id("rebuild")).click();   // page replaces the node

row.getText();                              // StaleElementReferenceException

Why a wait does not help. The wait already succeeded. You have the element. The problem is that the thing it points at no longer exists. Waiting longer just means waiting longer with a dead handle.

Two fixes. Re-find the element after the page settles, which is the normal answer. Or, when a component rerenders while you are polling it, tell the wait to ride it out:

Wait<WebDriver> wait = new FluentWait<>(driver)
        .withTimeout(Duration.ofSeconds(5))
        .pollingEvery(Duration.ofMillis(200))
        .ignoring(StaleElementReferenceException.class);

The design fix, which is the best answer. Never store WebElement as a field on a page object. Store the By and find it fresh each time. A locator cannot go stale; an element can. This is also the strongest argument against PageFactory, whose whole model is cached element proxies.

Check yourself

Are Selenium's exceptions checked or unchecked?

You add a longer wait and still get StaleElementReferenceException. Why?

A test wraps a click in try/catch and prints a message. The button is missing. What happens?
