Locators

Eight ways to find an element. You will use two of them. This lesson covers all eight quickly, then spends its time on CSS and XPath, which is where the real skill is. Every selector on this page ran green in LocatorsTest.

The whole lesson in four lines

1. Eight By strategies exist. In practice you use cssSelector and xpath, plus id when the page is kind.
2. CSS is shorter and reads better. Use it by default.
3. XPath does two things CSS cannot: match on visible text, and walk up the tree.
4. A good locator describes what the thing is, not where it sits.

The eight strategies

StrategyExampleWhen
By.idBy.id("email")Always, if the page gives you one. Fastest and clearest.
By.nameBy.name("emailAddress")Form fields. Common and reasonably stable.
By.classNameBy.className("field")Rarely. See the trap below.
By.tagNameBy.tagName("li")Counting things. Almost never for targeting one.
By.linkTextBy.linkText("Read the terms and conditions")Links, whole text, exact match.
By.partialLinkTextBy.partialLinkText("terms and")Links where part of the text is dynamic.
By.cssSelectorBy.cssSelector("[data-testid='submit']")Your default. Most things.
By.xpathBy.xpath("//li[text()='Enterprise']")Text matching, and going up the tree.
The trap everybody hits once

By.className takes one class name, not a list. An element with class="plan featured" is not found by By.className("plan featured").

When you need both, use CSS: By.cssSelector(".plan.featured"). That is most of why By.className is rarely worth using.

XPath, and the two things only it can do

The everyday form looks like a path:

//input[@name='password']          any input with that name, anywhere
//*[contains(@class,'ui-')]        any element whose class contains that
(//li[@class='plan'])[1]           the first match, 1-based

Note // means "anywhere in the document" and / means "direct child". Those are the CSS a b and a > b in different clothes.

The answer to "why would you ever use XPath?"

1. It can match visible text. CSS has no way to do this at all.

//li[text()='Enterprise']

2. It can walk up the tree. CSS only ever goes downwards. XPath can go up and then back down.

//td[text()='Bob']/parent::tr/td[3]     find Bob, go up to his row, read column 3

Those two are the whole case for XPath. Everything else CSS does more neatly.

Row scoping, the pattern you will use most

Real applications are full of tables and lists. You almost never want "the third row". You want "the row for Chandra". That is one XPath shape, and it is worth being able to write from memory:

//tr[td[text()='Chandra']]/td[2]        the row containing Chandra, then its 2nd cell

Read it as: find a tr that has a td with this text, then take its second td. The outer brackets are a filter, not a position.

What makes a locator survive a redesign

This is the part interviewers actually care about, and it is a design question rather than a syntax one.

The rule

A good locator describes what the element is. A bad one describes where it currently sits. Layout changes every sprint. Identity does not.

PreferAvoidWhy
#email/html/body/div[2]/form/input[1]An absolute path breaks when anyone adds a wrapper div.
[data-testid='submit'].btn-primary-9f3a2bGenerated class names change on every build.
//tr[td[text()='Bob']]#users tr:nth-child(2)Row 2 becomes row 3 the moment data changes.
one clear attributefive chained conditionsThe longer the locator, the more ways it can break.

The best answer of all, and worth saying out loud: ask the developers for a data-testid. An attribute that exists only for testing cannot be broken by a redesign, because nothing else uses it. Framing it as a conversation with the dev team rather than a locator trick is what makes it a senior answer.

Relative locators, a Selenium 4 addition

import static org.openqa.selenium.support.locators.RelativeLocator.with;

driver.findElement(with(By.tagName("input")).toRightOf(By.id("city-label")));

Also above, below, toLeftOf and near. Genuinely useful when the only stable thing on the page is the label next to the field you want. Worth naming in an interview because it shows you know Selenium 4 and not just Selenium 2.

findElement versus findElements

findElementReturns one. Throws NoSuchElementException if there are none.
findElementsReturns a List. Returns an empty list if there are none. Never throws.

That difference is a common question. It also gives you the idiom for "check something is absent", which cannot be done with findElement without catching an exception:

Assert.assertTrue(driver.findElements(By.cssSelector(".error")).isEmpty());
