Lesson 02 · Selenium

Waits

The page is not ready and your test does not know it. This is the single biggest source of flaky UI tests, and "explain implicit versus explicit versus fluent" is close to guaranteed in an interview. Every number on this page was measured on your machine, on Selenium 4.21.0.

The whole lesson in four lines

1. An implicit wait answers one question: is it in the DOM yet? Set once, applies to every findElement.
2. An explicit wait waits for a condition, at one point in the test. Visible, clickable, text changed, anything.
3. Fluent is an explicit wait with the polling and the ignored exceptions typed out by hand. WebDriverWait is a FluentWait.
4. Never mix implicit and explicit. Measured below: asking for 6 seconds got 8.5.

The problem

Modern pages load, then keep changing. An API call finishes and a table appears. A spinner clears and a button turns on. Your test does not stop for any of that.

findElement asks the browser once. If nothing matches, it throws NoSuchElementException straight away.

driver.findElement(By.id("reveal")).click();
driver.findElement(By.id("delayed"));   // throws. The element arrives 3s later.

The obvious fix is Thread.sleep(3000). Do not do it, and be ready to say why. It costs three seconds even when the element was ready in 200ms, and it still fails on the day the server is slow. It is both slower and less reliable than waiting properly. Sleeps in a suite are the thing an interviewer is listening for.

1. Implicit wait

driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(10));

One line. Set it once, and every findElement call for the rest of that driver's life will retry instead of failing immediately. The default is 0.

It is global, it is invisible at the call site, and it does exactly one thing: it retries until the element is in the DOM.

Where it stops helping, and it fails silently

The practice page has a button that is present from the first millisecond but disabled for two seconds. findElement returns it instantly, so a 10 second implicit wait never engages at all.

Then the click does nothing. Chrome does not throw for a click on a disabled button. No exception, no error, nothing red. The test carries on and asserts against a page where the click never happened.

I expected an ElementNotInteractableException when I wrote this test. There isn't one. That is worse, and it is the honest version of the story.

So an implicit wait cannot wait for: visible, enabled, clickable, the text to change, an element to disappear, or a count of rows. All of those are normal things to wait for.

2. Explicit wait

WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));

WebElement delayed = wait.until(
        ExpectedConditions.visibilityOfElementLocated(By.id("delayed")));

This waits for a named condition, at one point in the test. It polls every 500 milliseconds, and it swallows NotFoundException while it polls so a missing element is not an error yet. If the condition never comes true it throws TimeoutException.

The two cases the implicit wait could not touch:

wait.until(ExpectedConditions.elementToBeClickable(By.id("later"))).click();

wait.until(ExpectedConditions.textToBe(By.id("status"), "complete"));

Conditions worth being able to name out loud:

ConditionWaits until
presenceOfElementLocatedit is in the DOM. May still be hidden.
visibilityOfElementLocatedin the DOM and displayed.
elementToBeClickablevisible and enabled.
textToBethe element's text equals what you said.
invisibilityOfElementLocatedit has gone, or hidden. The spinner case.
alertIsPresenta native alert has opened.
numberOfElementsToBethe locator matches exactly N things.

Presence versus visibility is a real interview follow-up. presence is satisfied by an element with display:none, and then your getText() returns an empty string and the assertion fails somewhere confusing. Reach for visibility unless you have a reason not to.

3. Fluent wait

Wait<WebDriver> wait = new FluentWait<>(driver)
        .withTimeout(Duration.ofSeconds(10))
        .pollingEvery(Duration.ofMillis(250))
        .ignoring(NoSuchElementException.class);

WebElement delayed = wait.until(d -> d.findElement(By.id("delayed")));

Three knobs: how long, how often, and which exceptions to swallow while polling.

The line that makes this question easy

WebDriverWait extends FluentWait. I checked the bytecode in selenium-support-4.21.0.jar on this machine: its constructor calls withTimeout(yourDuration), then pollingEvery(500ms), then ignoring(NotFoundException.class).

So they are not two mechanisms. Fluent is the general one; WebDriverWait is the same object with sensible defaults already filled in. Say that and you have answered better than someone reciting three bullet points.

Which means you only reach for FluentWait when you want to change one of those defaults. Polling a slow, expensive condition less often. Or ignoring StaleElementReferenceException on a table that rerenders underneath you, which is the classic real use.

4. Why you must not mix them

The Selenium documentation says it flatly:

Do not mix implicit and explicit waits. Doing so can cause unpredictable wait times. For example, setting an implicit wait of 10 seconds and an explicit wait of 15 seconds could cause a timeout to occur after 20 seconds.

That is a claim, so I measured it. Two tests, same missing element, same 6 second explicit wait. One has a 4 second implicit wait set, the other has none.

EXPLICIT ONLY:  explicit 6s               timed out after 6183ms
MIXED WAITS:    implicit 4s + explicit 6s timed out after 8526ms

You asked for six seconds and got eight and a half. Stable across runs, within about 50ms.

Why. The explicit wait polls by calling findElement. Once an implicit wait is set, each of those polls now blocks for up to four seconds on its own. A poll that starts just before the six second deadline still has to run to completion. So your real timeout is the explicit timeout plus up to one implicit wait, and nobody reading the test can see it.

The rule. Pick one. In practice: leave the implicit wait at 0, never set it, and use explicit waits everywhere. That is what a framework does, and it is the answer to "which do you use and why".
