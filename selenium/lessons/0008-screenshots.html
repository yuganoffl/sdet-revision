Lesson 08 · Selenium

Screenshots

Short lesson, and the one where the two courses meet. TestNG lesson 7 told you onTestFailure is where the screenshot goes. This is the other half: what actually takes it, and why the listener cannot reach your driver unless you have built for it. All measured on this machine.

The whole lesson in four lines

1. Cast the driver to TakesScreenshot, then getScreenshotAs(...).
2. Three output types: FILE to save, BYTES to attach to a report, BASE64 to embed in HTML.
3. FILE gives you a temp file. Copy it or you lose it.
4. Put it in a listener, not in your tests. One class covers every test in the suite.

Taking one

TakesScreenshot is a separate interface from WebDriver, so you cast:

File temp = ((TakesScreenshot) driver).getScreenshotAs(OutputType.FILE);

All the browser drivers implement it. The cast is safe in practice, and it is why the line looks odd the first time you see it.

The three output types

TypeYou getUse it for
OutputType.FILEa File in the temp directorysaving to disk yourself
OutputType.BYTESbyte[]attaching to Allure or a report, in memory
OutputType.BASE64Stringembedding straight into an HTML report
The bug everyone hits: "my screenshots disappeared"

OutputType.FILE returns a file in the system temp directory. It is deleted when the JVM exits. If you keep the File reference and never copy the bytes anywhere, you have nothing after the run.

File temp = ((TakesScreenshot) driver).getScreenshotAs(OutputType.FILE);

Files.createDirectories(out.getParent());
Files.copy(temp.toPath(), out, StandardCopyOption.REPLACE_EXISTING);   // this line

Older tutorials use FileUtils.copyFile from Apache Commons IO. That works, but it is a whole dependency for one line that java.nio.file.Files already does.

Element screenshots, a Selenium 4 addition

Since Selenium 4, WebElement implements TakesScreenshot too. You can capture one component instead of the whole viewport, which makes a report much easier to read.

WebElement table = driver.findElement(By.id("users"));
File justTheTable = table.getScreenshotAs(OutputType.FILE);

Measured on this page: the full viewport came out at 50,012 bytes and the single table at 9,130 bytes. The test asserts that relationship rather than describing it.

Worth knowing for a follow-up: a plain Selenium screenshot captures the viewport, not the whole scrollable page. Full-page capture is not part of the W3C WebDriver standard, so it needs a browser-specific command or a scroll-and-stitch helper. Saying that is a better answer than assuming it grabs everything.

Where it actually belongs

Never in your tests. You would write the same six lines four hundred times, and every test would carry code about diagnosing itself.

One listener covers the whole suite:

public class ScreenshotListener implements ITestListener {

    @Override
    public void onTestFailure(ITestResult result) {
        WebDriver driver = DriverManager.get();
        if (driver == null) return;              // @BeforeMethod may have failed

        try {
            File temp = ((TakesScreenshot) driver).getScreenshotAs(OutputType.FILE);
            Files.createDirectories(OUT);
            Files.copy(temp.toPath(), OUT.resolve(name), REPLACE_EXISTING);
        } catch (IOException | RuntimeException e) {
            // swallowed on purpose, see below
        }
    }
}

Attach it with @Listeners(ScreenshotListener.class) on the class, or in testng.xml for the whole suite.

The design point, and it is the best thing in this lesson

A listener is handed an ITestResult. It cannot see a private WebDriver field on your test class.

So the driver has to live somewhere both can reach. That is DriverManager, and it is the practical reason the class exists, before you even get to thread safety.

Say this in an interview and you have connected your listener design to your driver design in one sentence. Most people describe them as two unrelated features.

Three details that make it production code

Null-check the driver. If @BeforeMethod failed, there is no browser. A listener that throws here replaces your real failure with a NullPointerException from the listener, which is a genuinely horrible thing to debug.

Swallow exceptions, and only here. This is the exception to lesson 5's rule. A screenshot that fails must not take down the report. It is diagnostics, not the test.

Name the file so it is findable. Class, method and a timestamp:

ScreenshotTest.thisOneFailsWhenYouFlipTheConstant-20260829-164835-309.png

The timestamp matters because a retried test writes twice, and a fixed name would overwrite the first attempt, which is usually the interesting one.

The gotcha from TestNG lesson 7, and it still applies

A retried attempt fires onTestSkipped, not onTestFailure. So a screenshot listener that only implements onTestFailure captures nothing for the attempts you most want to see.

If you use IRetryAnalyzer, take the screenshot in onTestSkipped too.

What else to capture, and why it matters more than the image

A screenshot alone often shows a normal-looking page. The context is what closes the bug. On failure, log:

  • the URL, driver.getCurrentUrl(), because the test may have been on the wrong page entirely
  • the browser and version, for a failure that only happens on Firefox
  • the data row, if it came from a @DataProvider
  • the page source, when the element was missing rather than wrong
  • the browser console logs, which catch the JavaScript error behind a blank page

Framework brief criterion 4 is exactly this: "a failure produces enough evidence to diagnose it without rerunning". A screenshot is one piece of that, not the whole of it.

Run it

mvn test -Dsurefire.suiteXmlFiles=selenium.xml -Dtest=ScreenshotTest

Five tests, green, and a real .png lands in target/screenshots/.

Then the part worth doing. Open ScreenshotTest.java, set FAIL_ON_PURPOSE to true, and rerun. One test fails, and the listener writes a second file:

SCREENSHOT  target/screenshots/ScreenshotTest.thisOneFails...-20260829-164835-309.png
            (url was file:///.../pages/lesson4.html)

Note what that failing test contains about screenshots: nothing. That is the whole point of the listener. Set the constant back to false when you are done.
